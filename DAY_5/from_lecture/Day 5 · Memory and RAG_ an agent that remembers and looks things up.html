02Conversation memory: checkpointer and thread_id

Instead of keeping a history list yourself, give the agent a checkpointer. It saves each conversation under a thread_id, one per customer chat.

On Days 2 and 4 you kept history in a variable and passed it back every time. That works for one customer. With many customers chatting at once, you need one separate history for each. LangChain does this for you: pass a checkpointer when creating the agent, and a thread_id with every message.

from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(model=llm, tools=[get_price, is_open, log_order],
                     system_prompt=SYSTEM, checkpointer=InMemorySaver())

def chat(thread_id: str, text: str) -> str:
    config = {"configurable": {"thread_id": thread_id}}
    result = agent.invoke({"messages": [{"role": "user", "content": text}]}, config)
    return result["messages"][-1].content

chat("ravi", "Hi, I'm Ravi. I want 2 plum cakes.")
chat("sravani", "Hello! Do you make cupcakes?")
chat("ravi", "Make them eggless please.")      # remembers: the plum cakes

Now you send only the new message. The checkpointer finds that thread's earlier messages and adds them. InMemorySaver keeps them in Colab's memory, so they are lost when the runtime restarts; in Week 2 we can save them to a file or database.

03Why not put everything in the prompt?

With 10 facts, the prompt is fine. With hundreds of policies, sending all of them on every message wastes money and buries the one fact that matters.

Remember Day 1: you pay for every input token on every call, and an agent makes several calls per question. A 30-page policy document in the system prompt is paid for again and again, even when the customer only asks about candles. Long prompts are also slower, and the model can miss the important line among many unrelated ones. The better way: find the 2–3 relevant facts first, and send only those.

04Embeddings: meaning as numbers

An embedding turns a piece of text into a list of numbers. Texts with similar meaning get similar numbers, even if they use different words.

"Do you deliver?" and "Can you send the cake to my house?" share almost no words, but they mean nearly the same thing. A keyword search would miss the link; embeddings catch it. An embedding model (a small, cheap model, different from the chat model) turns each sentence into a few hundred numbers, like coordinates. Close coordinates = close meaning. The closeness score is often called similarity.

A map of meaning (simplified to 2 dimensions)Live
Real world

When you search a shopping app for "something to keep my phone safe" and it shows phone cases, or a music app suggests songs that feel similar, embeddings are usually doing the work behind the scenes.

Analogy

A supermarket layout: things that belong together sit on nearby shelves (soaps near shampoos, rice near dal). Embeddings put sentences on a "shelf map" so that similar meanings sit close together.

05A vector database: ChromaDB

A vector database stores each text with its embedding, and finds the texts closest in meaning to a question.

ChromaDB is a free vector database that runs inside Colab. You give it texts; it makes the embeddings for you with a small built-in model (no API key needed), stores them, and answers "which texts are most similar to this question?".

import chromadb

client = chromadb.Client()                                   # an in-memory database
faq = client.get_or_create_collection(name="sweet_crumbs_faq")   # like a table

faq.add(
    ids=["delivery", "payment", "photo_cake"],
    documents=[
        "We deliver within 5 km of the bakery. Delivery is Rs 50, free for orders above Rs 1,000.",
        "We accept UPI and cash. Orders above Rs 1,000 need a 50% advance by UPI.",
        "Photo cakes and custom designs need 48 hours' notice.",
    ],
)

results = faq.query(query_texts=["Can you send the cake to my house?"], n_results=2)
print(results["documents"][0])    # the 2 closest texts, best match first

06Chunking: cut documents into the right pieces

Long documents are split into small pieces called chunks before they are stored. Each chunk should hold one idea.

If you store a whole 10-page policy as one item, every search returns all 10 pages, which defeats the purpose. If you cut it too small, a sentence gets split and loses its meaning. Good chunks are a few sentences about one topic. A small overlap (repeating a little text between neighbouring chunks) stops important sentences being cut in half.

def chunk(text: str, size: int = 300, overlap: int = 50) -> list[str]:
    """Split text into pieces of about `size` characters that overlap by `overlap`."""
    pieces, start = [], 0
    while start < len(text):
        pieces.append(text[start:start + size])
        start += size - overlap
    return pieces

For Sweet Crumbs the easiest chunking is natural: one FAQ = one chunk. For long PDFs, libraries such as LangChain's text splitters cut by paragraphs and sentences for you.

07RAG: retrieve, then answer

RAG = Retrieval-Augmented Generation: find the relevant facts, add them to the prompt, then let the model answer from them.

  1. Retrieve: search the vector database with the customer's question.
  2. Augment: put the top results into the prompt as "facts you may use".
  3. Generate: the model answers only from those facts, or says it will check with the owner.

With an agent, the cleanest way is to make retrieval a tool. The agent decides when a question is about a policy and calls it:

@tool
def search_faq(question: str) -> str:
    """Search Sweet Crumbs' policies and FAQs: delivery, payment, cancellation,
    photo cakes, allergens, storage, candles and messages on cakes.
    Use for any question about rules or policies, not for prices or opening hours."""
    results = faq.query(query_texts=[question], n_results=3)
    return "\n".join(results["documents"][0])

And one line in the system prompt's RULES: "For policy questions, use search_faq and answer only from what it returns. If the answer isn't there, say you'll check with the owner."

Cell 3 · The agent with memory

from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent

SYSTEM = """ROLE:   You are the friendly assistant for Sweet Crumbs Home Bakery.
RULES:  Use get_price for prices and is_open for timings; never guess them.
        For any policy question, use search_faq and answer ONLY from what it returns.
        If the answer isn't there, say "I'll check with the owner."
        Before log_order, make sure you have name, item, quantity and pickup date; ask if missing.
FORMAT: Under 60 words, friendly, English or Telugu matching the customer."""

agent = create_agent(model=llm, tools=[get_price, is_open, log_order, search_faq],
                     system_prompt=SYSTEM, checkpointer=InMemorySaver())

def chat(thread_id: str, text: str) -> str:
    config = {"configurable": {"thread_id": thread_id}}
    try:
        result = agent.invoke({"messages": [{"role": "user", "content": text}]}, config)
        return result["messages"][-1].content
    except Exception as e:
        print("Agent error:", e)
        return "Sorry, I'm a little busy. Please try again in a minute."

print(chat("ravi", "Hi, I'm Ravi. Do you deliver? My order is about Rs 1,300."))
print(chat("ravi", "Does the plum cake have nuts?"))
print(chat("sravani", "Can I cancel tomorrow morning if I pick up tomorrow evening?"))
print(chat("ravi", "What's my name, and will I pay for delivery?"))   # memory + RAG together
